앞 글에서는 색 대비나 반응형 분기점처럼 코드 안쪽 이야기를 적었다. 이 글은 그보다 한 겹
위, **일하는 과정에서 부딪힌 문제들**을 남긴다. 기술이 어려워서 막힌 건 거의 없었다.
막힌 건 대부분 **내가 세운 전제가 틀렸을 때**였다.

| 항목 | 결과 |
| --- | --- |
| 작업 시간 | 2026-09-07 밤 ~ 09-08 저녁 |
| 커밋 | 10개 |
| 방향을 되돌린 횟수 | 3번 |
| 헛수고한 작업 | 1건 (API 초안 + 목 서버) |
| 보안 이슈 | 2건 (둘 다 설정 문제) |

## 1. 없다고 생각한 백엔드가 이미 있었다

가장 크게 헛수고한 부분이다.

PRD를 검토하면서 "백엔드 API가 22개인데 전부 미확정"이라고 판단했다. 프론트엔드가
백엔드를 기다리지 않게 하려고 OpenAPI 스펙 초안을 쓰고, 그걸로 타입을 생성하고, MSW로
목 서버를 깔았다. 핸들러 22개에 목 데이터 548줄까지 만들었다.

그런데 목을 다 만들고 화면을 붙이려는 순간, 프로젝트 안에 이런 파일들이 보였다.

```
src/lib/supabase/     인증
src/app/api/generate/ 생성 API
src/lib/deck/         PPTX 제작
supabase/migrations/  DB 스키마
```

**이미 동작하는 풀스택 구현이 있었다.** 내가 목을 만드는 동안 다른 세션이 병렬로 만들고
있었던 것이다.

두 계약의 규모가 완전히 달랐다.

| | 내 초안 | 실제 구현 |
| --- | --- | --- |
| 엔드포인트 | 22개 | **1개** (`POST /api/generate`) |
| 입력 | 파일 20개 × 50MB | 텍스트 5,000자 또는 PDF 10MB |
| 흐름 | 프로젝트 → 자료 → 검토 → 폴링 → Revision | 단일 동기 요청 |

내 스펙은 PRD 문서를 그대로 옮긴 것이고, 실제 구현은 "가장 작게 동작하는 것"을 먼저 세운
것이었다. 어느 쪽이 틀린 게 아니라 **목표 범위가 달랐다.**

작업을 멈추고 물어봤고, 실제 구현을 정본으로 정했다. 만든 목은 지우지 않고 연결만 끊어서
남겼다. 왜 끊었는지와 되살리는 조건을 README에 적어뒀다. 나중에 프로젝트 관리 기능으로
확장할 때 참고가 되기 때문이다.

**교훈**: "없다"고 판단하기 전에 실제로 있는지 봐야 했다. `find src -type f` 한 번이면
됐다. 문서(PRD)만 읽고 코드를 보지 않은 게 원인이었다.

## 2. 증상이 같다고 원인이 같은 게 아니다

익명 키로 API를 찔러보니 남의 자료가 전부 조회됐다. 저장된 PPTX도 그대로 다운로드됐다.

나는 "마이그레이션이 절반만 적용됐다"고 단정하고, 보고서를 쓰고, RLS 정책을 다시 세우는
SQL까지 만들었다. 그런데 실제 상태를 조회해보니 이랬다.

```
decks RLS            활성
storage.objects RLS  활성
정책                 6개 전부 존재
버킷                 비공개
```

**전부 정상이었다.** 원인은 환경변수에 공개용 키 대신 비밀 키가 들어간 것이었고, 그 키는
설계상 RLS를 우회한다. 잠금은 다 채워져 있었고 마스터 키가 공개 자리에 놓여 있었다.

내가 만든 복구 SQL은 쓸 데가 없어서 지웠다. 확인에 1분도 안 걸리는 걸 안 하고 30분치
작업을 한 셈이다.

**교훈**: 고칠 곳을 정하기 전에 지금 상태를 조회한다. 증상 추론으로 단정하지 않는다.

## 3. 최신 버전이 내가 아는 버전이 아니었다

프레임워크를 제안할 때 "Next.js 15"라고 했다. 실제로 설치해보니 **16.3.4**였다.

버전 하나 차이가 아니었다. Next 16에서 `middleware.ts`가 `proxy.ts`로 개명됐고,
공식 문서가 이렇게 못 박고 있었다.

> proxy는 낙관적 체크에만 쓰고 전체 세션 관리·인가 수단으로 쓰지 말 것

내가 프레임워크를 추천할 때 든 근거 중 하나가 "미들웨어 인증 게이트"였다. 그 근거가
약해진 것을 그대로 말하고 정정했다. 프레임워크 선택 자체는 유지됐지만(결정적 이유는
이미지 최적화였다), 인증 구조는 다시 잡았다.

Next 16은 자기 문서를 `node_modules/next/dist/docs/`에 번들로 넣어둔다. 설치된 버전의
문서를 바로 읽을 수 있어서, 학습 데이터에 없는 변경도 확인이 됐다.

**교훈**: 버전은 기억으로 답하지 않는다. 설치해서 확인한다.

## 4. 같은 파일을 둘이 동시에 고쳤다

이 저장소를 두 세션이 동시에 편집하고 있었다. `page.tsx`가 몇 분 간격으로 오갔다.

```
23:09  내가 목 확인 페이지로 씀
23:10  다른 세션이 실제 화면으로 덮어씀
```

파일 목록을 확인하다가 `generate-form.tsx`가 있었다 없었다 해서, 한때는 "내가 남의 작업을
지웠나" 걱정했다. 확인해보니 **순서가 반대**였다. 내 임시 페이지가 실제 구현으로 교체된
것이고 잃은 건 없었다.

그 뒤로는 공유 파일을 덮어쓰기 전에 항상 최근 변경을 봤다.

```bash
find src -type f -newermt "-30 minutes"
```

그리고 전체 덮어쓰기 대신 정밀 치환으로 바꿨다. 앵커 문자열을 찾아서 그 부분만 바꾸는
방식이면, 상대가 이미 고쳐놨을 때 앵커가 안 맞아서 실패한다 — 조용히 덮어쓰는 것보다
실패하는 게 낫다.

나중에는 LLM 호출부가 별도 서버로 분리되는 큰 변경도 있었는데, 그건 커밋 이력을 보고
알았다.

**교훈**: 여러 사람(또는 세션)이 만지는 저장소에서는 "내가 마지막으로 본 상태"를
믿으면 안 된다.

## 5. 설정 함정 다섯 개

기술이 아니라 설정 때문에 막힌 것들이다. 하나같이 원인을 알고 나면 허무한데, 모르면 한참
헤맨다.

| 문제 | 원인 | 해결 |
| --- | --- | --- |
| `create-next-app` 실패 | npm 패키지명에 대문자 불가 | 소문자로 만들어 폴더만 대문자로 |
| GitHub 푸시 거부 (GH007) | 커밋 이메일이 개인 주소 | 저장소에만 noreply 주소 설정 |
| `.env.local.example`이 안 올라감 | `.env*` 규칙이 example까지 잡음 | `!.env*.example` 예외 추가 |
| MCP 서버를 못 씀 | 프로젝트 범위 설정인데 다른 폴더에서 세션 시작 | 작업 디렉터리를 옮김 |
| `npm run` 이 command not found | `tsx`가 devDependency에 없음 | 설치 |

마지막 것은 **내가 만든 문제**였다. 스크립트를 만들 때 `npx tsx`로 실행해서 그 자리에서는
됐는데, `package.json`에는 `tsx`를 직접 부르게 적었다. `npx`는 없으면 임시로 받아오지만
`npm run`은 그렇지 않다.

문서에 "검증 명령"이라고 적어둔 게 실행 불가 상태였다. 며칠 뒤에 그 문서를 믿고 실행한
사람은 시작부터 막혔을 것이다.

**교훈**: `npx`로 때우면 그 순간은 넘어가지만 다음 사람이 밟는다. 문서에 적는 명령은
문서에 적힌 그대로 실행해봐야 한다.

## 6. 보안 이슈 둘 — 둘 다 설정이었다

**첫째**, 공개용 환경변수에 비밀 키가 들어가 있었다. `NEXT_PUBLIC_` 접두사가 붙은 값은
빌드할 때 브라우저 번들에 박히므로, 그 키는 15개 파일에 인라인돼 있었다. git은 깨끗했지만
(커밋 이력 0건) 노출 경로가 저장소가 아니라 빌드 산출물이었다.

키를 공개용으로 바꾸고, 노출된 키는 삭제하고, 번들을 다시 빌드했다. 그리고 눈으로 보지
말고 검사하게 스크립트를 만들었다.

**둘째**, LLM 호출을 담당하는 로컬 서버의 인증이 전혀 작동하지 않았다.

```js
if (SECRET && req.headers["x-api-key"] !== SECRET) { /* 401 */ }
```

`SECRET`이 `undefined`면 이 조건 자체가 거짓이 되어 검사가 통째로 건너뛰어진다.
왜 `undefined`였냐면 — `tsx`는 `.env.local`을 자동으로 읽지 않는다. Next.js가 읽는
것이고 순수 Node 스크립트는 안 읽는다.

게다가 서버가 `0.0.0.0`에 바인딩돼 있어서 같은 공유기의 누구나 이 계정의 LLM 사용량을
쓸 수 있는 상태였다.

세 가지를 고쳤다.

```
tsx --env-file=.env.local     환경변수를 읽게
server.listen(PORT, "127.0.0.1")  루프백만
SECRET 없으면 기동 중단          경고만으론 지나친다
```

마지막이 중요하다. 원래 코드는 SECRET이 없으면 경고 로그만 찍고 그냥 떴다. 경고는 스크롤에
묻혀서 안 읽힌다. **안전하지 않은 상태로는 아예 뜨지 않게** 하는 편이 낫다.

## 7. 도구가 막아준 것들

이건 문제라기보다 안전장치가 작동한 기록이다.

- `.env.local`을 백업하려고 `cp`를 실행했더니 훅이 막았다. 시크릿을 여러 곳에 복사하는
  건 좋지 않으니 백업 없이 진행했다.
- `rm -rf .next`가 권한에서 거부됐다. 직접 실행하도록 명령을 넘겼다.
- 노출된 키를 삭제하려는데 **403**이 떴다. MCP에 설정된 토큰이 조회와 SQL 실행만
  가능하고 키 관리 권한이 없었다. 최소 권한이 지켜져 있던 것이라 오히려 바람직했다.
- README에 예시로 적은 `cp ... .env.local` 문장을 훅이 실제 명령으로 오탐해서 파일 쓰기가
  막혔다. 이건 과탐이지만, 이런 방향의 오차는 반대보다 낫다.

## 8. 한국어 UI의 함정

키를 삭제하려는데 확인 다이얼로그가 이렇게 물었다.

```
확인하려면 기본값을 입력하세요.
```

한글로 "기본값"을 넣으면 버튼이 계속 잠긴 상태였다. 원문은 `Type default to confirm`
이고, 키 이름이 `default`였던 것이다. **번역이 값 이름까지 번역해버린 경우**다.

입력해야 하는 건 영문 `default`였다.

## 정리하며

오늘 부딪힌 문제 대부분은 코드가 어려워서가 아니었다. **내가 확인하지 않은 것을 확인했다고
생각한 데서** 나왔다.

- 백엔드가 없다고 생각했는데 있었다 → 코드를 안 봤다
- RLS가 안 걸렸다고 생각했는데 걸려 있었다 → 상태를 안 조회했다
- Next 15라고 생각했는데 16이었다 → 설치해보지 않았다
- 검증 명령이 된다고 생각했는데 안 됐다 → `npm run`으로 실행해보지 않았다

네 개가 같은 모양이다. 판단하기 전에 한 번 보면 되는 것들이었고, 확인 비용은 다 1분 미만
이었다.

방향을 세 번 되돌렸는데, 세 번 다 대화 중에 잡혔다. "그 전제가 맞나"를 물어봐 주는 상대가
있는 것과 없는 것의 차이가 컸다. 혼자였으면 목 서버 22개를 다 붙이고 나서야 알았을 것이다.

그리고 겪은 함정은 전부 프로젝트의 `AGENTS.md`에 적어뒀다. 다음에 같은 저장소를 여는
사람이(또는 내가) 처음부터 다시 밟지 않도록.

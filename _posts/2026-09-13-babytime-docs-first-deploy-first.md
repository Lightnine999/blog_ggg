육아 기록 앱을 하나 만들기 시작했다. 아침엔 기획서 한 장 없었고, 밤엔 실제로
가입하고 로그인해서 아기 수유를 기록할 수 있는 앱이 배포돼 있었다.

먼저 역할을 분명히 해두면, **무엇을 만들지 정하고 결정을 내린 건 나**고,
**코드와 문서를 쓰고 검증을 돌린 건 세션(Claude Code)**이다. Supabase 프로젝트를
만들고 대시보드를 설정하고 실제로 가입 테스트를 해본 것도 나다. 아래 "배운 것"은
전부 그 과정에서 내가 직접 보고 알게 된 것들이다.

| 항목 | 결과 |
| --- | --- |
| 오늘 커밋 | 31개 |
| 변경 | 82개 파일 (+8,785 / −1,335) |
| 문서 | 10종 약 3,800줄 |
| 검증 스크립트 | 6개 |
| 테스트 | 69건 |
| 배포까지 걸린 시간 | 22분 |

---

## 1단계. 코드보다 문서를 먼저 썼다

첫 요청이 "PRD와 기술 명세서 2개를 먼저 쓰자"였다.

결과적으로 이게 오늘 제일 잘한 선택이었다. 하루에만 요구사항이 **세 번** 바뀌었기 때문이다.

- 커뮤니티 기능을 넣기로 → 뺐다가 → 다시 넣기로
- 얼굴 블러를 Phase 2로 미뤘다가 → "제공하되 직접 만들진 말자"로

문서가 있으니까 **바꿀 때마다 어디를 고쳐야 하는지가 분명했다.** 문서가 없었으면
"아까 뭐라고 했더라"를 매번 되짚어야 했을 것이다.

### 배운 것 — 문서 3종은 묻는 질문이 다르다

문서가 여러 개로 나뉘는데, 각각 보는 각도가 다르다.

| 문서 | 묻는 질문 | 언제 보나 |
| --- | --- | --- |
| 작업 명세 | "이거 다 만들었나?" | 작업 단위마다 |
| 운영 체크리스트 | "설정을 켰나?" | 오픈 전 |
| 최종 검증 | "실제로 도나? 이상하게 써도 버티나? 안전한가?" | 오픈 직전 |

그리고 하나 더. **같은 내용을 두 문서에 적으면 반드시 한쪽이 낡는다.** 그래서
기능 목록은 기획서에만, DB 구조는 기술명세에만, 진행 상태는 작업명세에만 두기로 했다.

---

## 2단계. 결정을 먼저 못박았다

기획서에 "아직 못 정한 것" 목록을 만들어서 하나씩 답을 정했다. 아홉 개였다.

- 이메일 인증을 필수로 할까? → **필수로**
- 아기 여러 명 등록을 언제 넣을까? → **처음부터**
- 커뮤니티를 MVP에 넣을까? → 뺐다가 **다시 넣기로**
- 비로그인도 볼 수 있게 할까? → **아니오, 로그인해야만**

### 배운 것 — 번복해도 되지만, 이유는 남겨야 한다

커뮤니티를 뺐다가 다시 넣었을 때, 문서에 "왜 뺐는지"와 "왜 다시 넣는지"가 같이 남았다.
덕분에 나중에 또 흔들려도 이미 검토한 논점을 다시 파지 않아도 된다.

## 3단계. 빈 껍데기라도 배포부터 했다

"오늘 3시간 안에 한 바퀴 돌려서 서버에 올라가는 것까지 보고 싶다"고 했더니,
기능을 만들기 전에 **GitHub 저장소 만들고 Vercel에 올리는 것부터** 했다.

22분 만에 배포까지 갔다. 그때 올라간 건 로그인 화면 정도밖에 없는 껍데기였다.

### 배운 것 — 배포 경로를 먼저 뚫어두면 나중에 시간을 안 뺏긴다

기능을 다 만들고 마지막에 배포하려 했으면, 그날 "왜 안 올라가지"로 시간을 다 썼을 것이다.
실제로 첫 푸시에서 **GitHub 이메일 비공개 설정 때문에 거부**당하는 일이 있었다.
껍데기 상태라 1분 만에 고쳤지, 마지막 날이었으면 당황했을 것이다.

---

## 4단계. 작업을 24조각으로 쪼갰다

내가 제안한 방식이다. 큰 작업을 한 번에 몰아서 하지 말고, 작게 나눠서 하나씩
확인하면서 가자고 했다. 이유는 두 가지였다.

1. 한 번에 크게 하면 어디서 틀렸는지 찾기 어렵다
2. AI랑 작업할 때 한 세션이 너무 길어지면 앞부분을 잊어버리거나 실수가 늘어난다

그래서 전체를 **U01~U24**로 나누고, 한 단위가 끝나면 **인수인계 문서**를 남겨서
다음 세션이 그것만 읽고 이어받게 했다.

### 배운 것 — "다 됐다"가 아니라 "이 명령이 통과했다"

완료 조건을 말이 아니라 **실행 가능한 명령**으로 적기로 했다.

```bash
npm run build && npx vitest run && npx eslint .
```

이게 초록불이면 끝, 아니면 안 끝난 것. "될 것 같다"는 안 끝난 것으로 친다.

그리고 각 조각은 **혼자서 확인 가능해야 한다**는 조건을 넣었다.
"다음 조각이 끝나야 확인 가능"하면 잘못 쪼갠 것으로 본다.

## 5단계. Supabase를 붙였다 — 전용 프로젝트를 새로 만든 이유

로그인을 직접 만들지 말고 검증된 서비스에 맡기자고 해서 Supabase를 쓰기로 했다.

처음엔 **예전에 쓰던 Supabase 프로젝트를 같이 쓰면 되지 않나** 싶어서
"공유해서 같이 쓰자, 문제 있을까?" 하고 물었다. 답은 "문제 있다"였다.

### 배운 것 — `auth.users`는 프로젝트에 하나뿐이다

Supabase에서 로그인 사용자 정보는 프로젝트마다 **딱 하나의 테이블**에 모인다.
두 앱이 한 프로젝트를 쓰면 이런 일이 생긴다.

- **한쪽에서 탈퇴하면 다른 앱의 데이터까지 같이 지워진다** (연쇄 삭제)
- 이메일 인증을 켜면 **두 앱 모두** 켜진다 (설정이 프로젝트 단위)
- 인증 메일이 돌아올 주소(Site URL)는 **프로젝트당 하나뿐**이다

특히 첫 번째가 걸렸다. 결국 전용 프로젝트를 새로 만들었는데 3분밖에 안 걸렸다.
공유했으면 나중에 탈퇴 기능을 켜는 순간 다른 앱 데이터가 같이 지워졌을 것이다.

## 6단계. 여기서 오늘 제일 많이 배웠다 — 검증

기능을 만드는 것보다, **제대로 도는지 확인하는 것**에서 더 많이 배웠다.

### 6-1. 로컬에선 멀쩡한데 배포본에서만 깨지는 버그

가입하고 인증 메일 링크를 눌렀는데 이 화면이 떴다.

```
사이트에 연결할 수 없음
localhost에서 연결을 거부했습니다.
ERR_CONNECTION_REFUSED
```

원인은 이랬다. 우리 앱은 "인증 끝나면 배포 주소로 돌려보내 줘"라고 보내는데,
**Supabase는 그 주소가 허용 목록에 없으면 오류를 내지 않고 조용히 기본값으로 바꿔버린다.**
기본값이 `localhost`였다.

이게 왜 고약하냐면:

- **에러 로그가 안 남는다.** 조용히 대체하니까
- **로컬에서 개발 서버를 켜두면 우연히 동작한다.** 그래서 개발할 땐 멀쩡해 보인다
- **배포본에서만 깨진다.** 실제 사용자만 못 쓴다

확인하려고 로컬 서버를 끄고 다시 가입해봤다. 그제서야 확실해졌다.

지금은 이 한 줄로 확인한다.

```bash
bash scripts/check-redirect-allowlist.sh
```

원리는 이렇다. **일부러 틀린 토큰으로 인증 요청을 보낸다.** 인증은 실패하지만,
Supabase가 "어디로 돌려보내려 했는지"가 응답 헤더에 그대로 나온다. 계정도 안 만들어지고
아무것도 소비하지 않는다.

### 6-2. 보안 헤더는 기본으로 안 붙는다

배포본을 검사했더니 보안 헤더가 **다섯 개나 없었다.**

- `X-Frame-Options` — 내 사이트를 남의 페이지에 몰래 끼워 넣는 공격(클릭재킹) 방어
- `X-Content-Type-Options` — 파일 종류를 브라우저가 멋대로 추측하는 것 방지
- `Referrer-Policy` — 외부로 나갈 때 내 페이지 주소가 새는 것 방지
- `Permissions-Policy` — 안 쓰는 카메라·마이크 권한 차단
- `HSTS` — HTTPS 강제

Next.js는 이 헤더들을 기본으로 붙이지 않는다. 설정 파일에 직접 적어야 한다.

### 6-3. 색 대비는 눈이 아니라 계산으로

접근성 점검을 하는데, 화면을 눈으로 보면 멀쩡했다. 그런데 실제로 **계산**해봤더니
입력칸 테두리 대비가 **1.23 : 1**이었다. 기준은 3 : 1이다.

테두리가 입력칸의 유일한 경계인데, 시력이 약한 사람에게는 **칸이 어디 있는지 안 보이는
수준**이었다. 색을 바꿔서 3.37 : 1로 올렸다.

또 하나. 입력칸에 `outline-none`이라는 설정이 들어가 있었는데, 이게 **키보드로 탭을
눌러 이동할 때 지금 어디 있는지 보여주는 표시를 지우고 있었다.** 마우스 쓰는 사람은
평생 모를 문제다.

### 6-4. 스크립트가 실패를 숨기면 안 된다

환경변수를 등록하는 스크립트를 만들어서 돌렸는데, "완료"라고 나왔다. 그런데 확인해보니
**하나도 안 들어가 있었다.**

스크립트가 등록 명령의 출력을 버리고 **무조건 성공 표시를 찍고 있었다.** 실패해도
사용자는 완료된 줄 안다. 이걸 고치고 나서야 진짜로 등록됐다.

성공만 보여주는 자동화는 자동화가 아니라는 걸 배웠다.

## 오늘 확인하지 못한 것

정직하게 적어둔다. 이것들은 아직 "될 것 같다" 상태다.

- **계정 간 데이터 격리** — 내 계정으로 남의 아기 기록을 볼 수 있는지. 이 앱에서
  제일 위험한 부분인데 계정이 2개 필요해서 오늘은 못 했다. 오늘 가입 테스트를
  두 번 해서 계정이 2개 생겼으니 다음에 바로 할 수 있다
- **CSP** — 스크립트 삽입 공격 방어. 인증 흐름과 얽혀 있어서 대충 넣으면 앱이
  통째로 깨진다. 검증 가능한 환경에서 넣기로 했다
- 수면·기저귀·성장 기록의 실제 동작, 자정 넘어가는 수면 집계
- 법적 고지(약관·개인정보처리방침)는 **초안**이다. 법률 검토를 안 받았다

## 마치며

오늘 제일 크게 느낀 건 **"눈으로 확인하는 것"과 "확인했다고 말할 수 있는 것"은
다르다**는 점이었다.

화면은 멀쩡해 보였지만 테두리 대비는 기준 미달이었고, 스크립트는 완료라고 했지만
아무것도 안 들어가 있었고, 로컬에선 인증이 잘 됐지만 배포본에선 깨져 있었다.
셋 다 **명령을 돌려서** 잡았다.

그래서 체크리스트에 "✅"를 찍으려면 명령 출력이나 응답 코드 같은 근거가 있어야 한다는
규칙을 문서에 넣었다.

다음엔 계정 격리 검증부터 한다. 제일 위험한 것부터.

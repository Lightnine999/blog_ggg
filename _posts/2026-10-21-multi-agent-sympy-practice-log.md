## 1. 무엇을 비교하는 실습인가

학습자료의 목표는 같은 버그 수정 문제를 조율 방식만 달리 실행하고, 해결 여부와 비용을 기록으로 비교하는 것이다. 문제 모음은 [SunCreation/d035-agent-lab](https://github.com/SunCreation/d035-agent-lab)에서 내려받았다. 이 중 SymPy 문제 세 개를 사용했다.

| 인스턴스 ID | 문제 요약 |
| --- | --- |
| `sympy__sympy-24152` | 텐서곱을 전개할 때 두 번째 인수까지 전개되지 않는 문제 |
| `sympy__sympy-24213` | 같은 차원인 항들을 더할 때 차원이 다르다는 오류가 나는 문제 |
| `sympy__sympy-24909` | `milli * W`가 `1`이 되어 단위가 사라지는 문제 |

명령에 쓰는 이름은 문제 폴더명이 아니라 `info.json`의 `instance_id`다.

### 고정한 조건, 바꾼 조건, 측정한 값

| 구분 | 이번 실습의 설정 |
| --- | --- |
| 고정 | 같은 세 인스턴스, 실험 모델 별칭 `haiku`, 인스턴스별 기준 커밋, 새 체크아웃 준비, 채점 패치와 지정 테스트 |
| 조작 | 다음 행동을 결정하는 방식: 단일 에이전트 / 파이썬 워크플로 / 리드 모델 |
| 측정 | `resolved`, `invalid`, SDK 비용·턴 수·호출 시간, 별도 모델의 행동 점수 |

고정한 모델은 정확한 모델 버전 ID가 아니라 `haiku`라는 별칭이다. 장기 재현에서는 이 점도 고려해야 한다.

| 실행 | 조율 주체와 흐름 | 턴 예산 |
| --- | --- | --- |
| A | 에이전트 하나가 탐색과 수정 수행 | 최대 25턴 |
| B | 파이썬 코드가 locator → fixer 순서로 호출 | locator 12턴 + fixer 18턴 |
| C | 리드가 직접 진행하거나 locator에 탐색 위임 | 리드 최대 40턴 |

**턴 예산은 같지 않다.** B는 최대 30턴을 두 호출에 나누고, C에는 locator 자체의 12턴 제한을 별도로 명시하지 않았다. 따라서 조율 방식만의 효과를 엄격히 분리한 실험이라고 단정할 수 없다.

## 2. 실행 환경과 파일을 준비한 과정

2026년 10월 19일에 문제 저장소와 실행 파일을 준비했고, 10월 21일에 명령 실행과 결과 비교를 이어갔다. 로컬 작업 폴더는 `~/aiffel_work/Multi_agent_codex`다.

| 파일 | 역할 |

## 3. resolved와 invalid를 구분해서 읽기

| 항목 | 의미 | 판정 방법 |
| --- | --- | --- |
| `resolved` | 지정된 채점을 통과했는가 | `test_patch.diff` 적용 후 지정 테스트 종료 코드가 0이면 True |
| `invalid` | 테스트 수정 금지 규칙을 어겼는가 | 에이전트가 `tests/` 아래 파일을 바꿨으면 True |

`resolved=False, invalid=False`는 **규칙은 지켰지만 채점을 통과하지 못했다**는 뜻이다. 둘은 반대말이 아니다.

에이전트가 만든 `changes.diff`와 테스트 수정 여부를 먼저 저장한 다음, 평가기가 채점 패치를 적용한다. 평가기가 넣는 테스트는 에이전트의 규칙 위반으로 세지 않는다. 패치의 CRLF 줄바꿈은 LF로 정규화해 적용하도록 했다.

채점은 해당 폴더의 `.venv` 파이썬으로 수행한다. 다만 트랜스크립트에서는 에이전트가 자체 검증에 시스템 Python, Anaconda, 임시 가상환경을 사용하는 경우도 확인됐다. **최종 채점 환경과 에이전트가 자율적으로 선택한 검증 환경까지 모두 같았던 것은 아니다.**

## 5. 24909: 에이전트의 완료 보고와 채점 결과가 달랐다

A의 `result.json`에는 수정 완료 및 기존 units 테스트 72개 통과라는 에이전트 보고가 있다. 하지만 사후 채점의 `tail`에는 다음 실패가 남았다.

```python
assert m * k is S.One
```

채점 결과는 1개 실패, 2개 통과였다. B와 C도 같은 검증에서 실패했다.

수정은 `fact == 1`일 때의 `return 1`을 `other`가 `Prefix`인 분기 안으로 옮기는 것이었다. A와 C는 곱셈과 나눗셈을, B는 곱셈을 수정했다. A와 C의 diff는 같았다.

```diff
-        if fact == 1:
-            return 1
-        elif isinstance(other, Prefix):
+        if isinstance(other, Prefix):
+            if fact == 1:
+                return 1
```

증상에 대한 수정과 채점이 기대하는 동작 충족은 별개였다. 위 diff에는 여전히 파이썬 정수 `1`을 반환하는 경로가 있다. 실패한 검증은 값이 같은지를 보는 `==`가 아니라 SymPy의 `S.One`과 같은 객체인지 확인하는 `is`다.

Sonnet 판정의 사유에는 접두사를 유지하는 출력 형태를 핵심 원인으로 설명한 부분도 있다. 그러나 **실제로 제시된 실패 로그가 직접 보여 주는 것은 `m * k is S.One`의 실패**다. 출력 표기 문제와 이 실패의 인과관계를 판정문만으로 확정하지 않았다.

## 7. Sonnet 행동 판정과 그 한계

실험 모델은 Haiku, 판정 모델은 Sonnet으로 나눴다. `judge.py`는 각 실행의 `result.json`, 모든 `transcript*.jsonl`, `changes.diff` 전체를 입력에 넣고 `output_format`의 JSON Schema로 결과를 받는다. 판정 호출에도 `setting_sources=[]`를 넣었다.

| 점수 | 평가 대상 |
| --- | --- |
| 근거_추적 | 코드를 읽고 원인을 수정과 연결했는가 |
| 편집_최소성 | 문제와 관련된 최소한의 변경인가 |
| 검증_성실성 | 재현·테스트를 실제 수행하고 한계와 실패를 정직하게 보고했는가 |

각 점수는 0·1·2다. 스키마 키는 영문이고 저장할 때 점수와 실패 분류를 한글 키로 바꾼다. 모델이 만든 판정은 실행 폴더의 `judgment.json`, 전체 행은 작업 폴더의 `grading.jsonl`과 `results-table.md`에 남긴다.

```bash
# 모델 호출로 판정하고 집계
.venv/bin/python judge.py

# 판정을 새로 호출하지 않고 집계만 갱신
.venv/bin/python judge.py --aggregate
```

기본 명령은 기존 판정도 다시 호출한다. 재실행 시 비용이 추가될 수 있다. 집계 명령만으로 빠진 모델 판정이 채워지지는 않는다.

### 완료 상태

| 인스턴스 | 실행 | 근거 / 최소성 / 검증 | 실패 분류 | quote_found |
| --- | --- | --- | --- | --- |
| 24152 | A | 2 / 2 / 2 | 없음 | True |
| 24152 | B | 2 / 2 / 2 | 없음 | True |
| 24152 | C | 2 / 2 / 2 | 없음 | True |
| 24213 | A | 2 / 2 / 2 | 없음 | True |
| 24213 | B | 2 / 2 / 2 | 없음 | True |
| 24213 | C | 미판정 | 세션 한도 오류 | False |
| 24909 | A | 2 / 2 / 1 | 잘못된_수정 | True |
| 24909 | B | 2 / 2 / 1 | 잘못된_수정 | False |
| 24909 | C | 미판정 | 세션 한도 오류 | False |

9건 중 7건 판정 후 Claude 세션 사용 한도로 나머지 두 건이 실패했다. 두 건의 점수는 0이 아니라 null이다. 이는 실험 실행 실패와 별개다. C의 24213은 문제 해결 채점은 통과했지만 행동 판정이 누락된 경우다.

완료된 7건의 `judge_cost_usd` 합계는 약 **$14.36**였다. 버그 수정 실행 전체의 SDK 비용 합계 약 **$0.12157**와 별도로 봐야 한다. 원본과 SDK 스트림 전체를 함께 입력한 구현이라 중복 기록도 포함되지만, 비용의 원인별 기여까지 따로 분석하지는 않았다.

### 인용문을 원문으로 다시 확인하기

`quote_found`는 인용문이 트랜스크립트 원문 또는 JSON 디코딩된 문자열에 연속해서 존재하는지 확인한다. True라고 해석까지 옳다는 뜻은 아니다.

A의 24909 `judgment.json`에는 다음 인용이 있고, 트랜스크립트에 실제 존재함을 확인했다.

> The existing test `dodeca * m == 12 * m` requires folding the scale factor into a plain `Quantity`, so that behavior is intentional and I shouldn't remove it.

반면 B의 24909는 명령과 출력 사이를 화살표로 연결해 재구성한 문장을 인용으로 냈다. 그 문장 전체가 원문에 존재하지 않아 `quote_found=False`가 됐다. 이 판정의 점수는 저장돼 있지만, 검증된 원문 인용을 가진 판정과 같은 신뢰도로 취급하면 안 된다.

모델 판정도 검증 대상이라는 점을 이 과정에서 확인했다. 판정 오류 두 건과 인용 불일치 한 건은 수정해 숨기지 않고 현재 집계에 그대로 남아 있다.

## 8. SDK 안의 정의를 CLI 파일로 옮기기

처음에는 `.claude/agents/locator.md`가 없었고, locator는 `arms.py`의 파이썬 정의로만 존재했다. 파일 여부와 비슷한 코드 설정을 혼동하지 않도록 확인한 뒤, 별도 요청으로 다음 파일을 실제 생성했다.

```text
Multi_agent_codex/
├── arms.py
├── common.py
├── judge.py
├── locator-cli-guide.md
└── .claude/
    └── agents/
        └── locator.md
```

CLI 파일에는 `Read, Grep, Glob`, `model: haiku`, `maxTurns: 12`와 세 항목으로 보고하는 지침을 넣었다. 기존 C의 파이썬 정의에는 locator 전용 모델과 12턴 제한이 명시되어 있지 않았으므로 두 정의가 완전히 같은 설정은 아니다.

Claude Code에서는 프로젝트에서 새 세션을 열고 `@agent-locator`로 호출할 수 있다. 이번처럼 agents 폴더를 처음 만든 경우에는 세션 재시작이 필요하다. [공식 서브에이전트 문서](https://code.claude.com/docs/en/sub-agents)를 확인해 사용 안내를 작성했다.

**파일 생성과 내용 확인까지만 했고, 이 CLI 파일로 locator를 실제 호출하는 추가 실험은 하지 않았다.** 기존 `arms.py`와 결과도 바꾸지 않았다.

## 9. 이번 기록으로 내리는 제한적인 판정

이 세 문제의 실행 조건에서는 **A를 기준선으로 채택하고, B의 일괄 적용은 축소**한다는 판정이 가능하다. 각 방식이 같은 두 문제만 해결했고, B의 비용·호출 시간·턴 합계가 A보다 컸다는 `result.json` 집계 근거가 있기 때문이다. 이것은 이 세 문제와 이번 실행에 한정한 해석이며, 모든 버그 수정에 B가 불필요하다는 결론은 아니다.

C는 비용과 호출 시간 합계가 작았다는 관측을 남긴다. 다만 24909에서 실제 locator 위임이 없었으므로, 그 효율을 멀티 에이전트 협업의 이득으로 돌릴 수 없다. 행동 판정도 두 건이 빠져 A·B와 완전히 같은 조건으로 비교되지 않는다.

이번 실습은 세 문제를 방식별 한 번씩 실행한 경량 평가다. 반복 실행에 따른 편차, 모델 별칭의 변화, 턴 예산 차이, 에이전트 자체 검증 환경 차이를 통제하지 못했다. 이 범위를 넘어 우열을 일반화하지 않는다.

### 다시 실행한다면

아래는 아직 수행하지 않은 다음 실험 계획이다.

- 유지할 조건: 같은 인스턴스, 기준 커밋, 새 체크아웃, `.venv` 채점, 동일 테스트 패치.
- 비교를 보강할 조건: 정확한 모델 ID 기록, 방식별 자원 예산 기준 통일, 반복 실행, 자체 검증 파이썬 경로 명시.
- 조율 확인: C의 위임 횟수를 모든 실행에서 기록. 위임을 강제하는 변형은 기존 C와 분리해서 비교.
- 판정 보강: 중복 트랜스크립트 제거를 검토하고, 실패한 판정만 재시도하도록 개선. 원문과 맞지 않는 인용은 재검토 대상으로 남김.

이 과정에서 배운 것은 구성 이름으로 협업을 가정하지 않고 **실행 기록 → 채점 결과 → 인용 원문 → 제한적인 결론** 순서로 확인하는 방법이다.

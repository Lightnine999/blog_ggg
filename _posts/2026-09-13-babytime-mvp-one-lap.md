오늘 목표는 하나였다. **육아 기록 앱 MVP를 하루 안에 한 바퀴 돌려보는 것.**

"한 바퀴"의 기준은 이렇게 잡았다.

> 기획 → 코드 → 배포 → **실제로 가입하고 로그인해서 기록이 저장되는 것까지**

완성이 목표가 아니었다. **되는지 안 되는지를 오늘 안에 눈으로 보는 것**이 목표였다.

결론부터 말하면, 됐다. 밤에 실제로 가입하고, 메일 인증하고, 로그인해서,
아기를 등록하고, 수유를 기록했다.

| 항목 | 결과 |
| --- | --- |
| 만든 것 | 육아 기록 앱 (수유·수면·기저귀·성장) |
| 배포까지 | **22분** |
| 첫 로그인 성공까지 | 하루 |
| 커밋 | 31개 |
| 변경 | 82개 파일 (+8,785 / −1,335) |

작업 방식은 바이브코딩이었다. **무엇을 만들지 정하고 결정을 내린 건 나**고,
**코드를 쓴 건 세션(Claude Code)**이다. Supabase 프로젝트를 만들고 실제로
가입 테스트를 한 것도 나다.

---

## 왜 "한 바퀴"부터 돌리려 했나

기능을 아무리 많이 만들어도 **배포가 안 되거나 로그인이 안 되면 0**이다.
화면만 예쁘게 열 개 만들어놓고 마지막 날에 "왜 안 올라가지"를 시작하면
그날 하루를 통째로 날린다.

그래서 가늘어도 좋으니 **끝까지 이어지는 한 줄**을 먼저 만들기로 했다.
그 줄이 뚫리고 나면 그다음부터는 살만 붙이면 된다.

---

## 시간순으로 본 하루

### 아침 — 코드보다 문서 2개부터

첫 요청이 "PRD와 기술 명세서를 먼저 쓰자"였다. 바이브코딩이라도 **뭘 만들지는
내가 정해야** 하기 때문이다.

잘한 선택이었다. 하루에만 요구사항이 세 번 바뀌었다.

- 커뮤니티 기능을 넣기로 → 뺐다가 → 다시 넣기로
- 얼굴 블러를 나중으로 미뤘다가 → "제공하되 직접 만들진 말자"로

문서가 있으니 바꿀 때마다 **어디를 고쳐야 하는지가 분명**했다.

그리고 결정을 아홉 개 못박았다. 이메일 인증 필수, 아기 여러 명 등록, 로그인해야만
커뮤니티 열람 같은 것들이다. 이걸 먼저 정해두니 세션이 물어보는 횟수가 확 줄었다.

### 22분 — 껍데기라도 배포부터

"3시간 안에 서버에 올라가는 것까지 보고 싶다"고 했더니, 기능을 만들기 전에
**GitHub 저장소 만들고 Vercel에 올리는 것부터** 했다.

22분 만에 배포까지 갔다. 그때 올라간 건 로그인 화면 하나뿐인 껍데기였다.

그런데 바로 그 껍데기 단계에서 **GitHub이 푸시를 거부**했다. 이메일 비공개 설정
때문이었다. 껍데기라 1분 만에 고쳤다. 이걸 마지막 날에 만났으면 훨씬 당황했을 것이다.

### 낮 — 기능 붙이기

배포 경로가 뚫려 있으니 그다음부터는 빨랐다. 수유·수면·기저귀·성장 기록,
아기 여러 명 전환, 타임라인까지 붙였다.

기록 화면은 **탭 두 번, 3초 안에** 끝나게 만들었다. 한 손엔 아기, 한 손엔 젖병인
상태에서 쓰는 앱이라 입력이 길면 아무도 안 쓴다.

### 저녁 — Supabase 연결, 그리고 첫 로그인

로그인은 직접 만들지 않고 Supabase에 맡겼다. 여기서 하루의 클라이맥스가 나왔다.

처음엔 예전에 쓰던 Supabase 프로젝트를 같이 쓰면 되지 않나 싶어서
"공유해서 같이 쓰자, 문제 있을까?" 하고 물었다. 답은 "문제 있다"였다.

Supabase는 **로그인 사용자 정보가 프로젝트마다 딱 하나의 테이블**에 모인다.
두 앱이 한 프로젝트를 쓰면 **한쪽에서 탈퇴할 때 다른 앱 데이터까지 같이 지워진다.**
새 프로젝트를 만드는 데 3분 걸렸다.

연결하고 나서 실제로 가입해봤다. 그리고 **첫 벽에 부딪혔다.**

---

## 한 바퀴 돌리다 걸린 것들

### 인증 메일 링크를 눌렀더니 연결이 거부됐다

```
사이트에 연결할 수 없음
localhost에서 연결을 거부했습니다.
ERR_CONNECTION_REFUSED
```

우리 앱은 "인증 끝나면 배포 주소로 돌려보내 줘"라고 보내는데,
**Supabase는 그 주소가 허용 목록에 없으면 오류를 내지 않고 조용히 기본값으로 바꾼다.**
기본값이 `localhost`였다.

이게 MVP 돌려보기에서 특히 성가신 이유가 있다.

- **에러 로그가 안 남는다.** 조용히 대체하니까
- **로컬 개발 서버를 켜두면 우연히 동작한다.** 그래서 개발 중엔 멀쩡해 보인다
- **실제 사용자만 못 쓴다**

로컬 서버를 끄고 다시 가입해보고 나서야 확실해졌다. 설정 고치고 다시 해보니
이번엔 배포 주소로 제대로 돌아왔다. 그게 오늘 **첫 로그인**이었다.

### 눈으로 봐선 멀쩡한데 기준 미달이었던 것들

배포본을 검사해보니 **보안 헤더가 다섯 개** 빠져 있었다. 클릭재킹 방어,
MIME 스니핑 방지 같은 것들인데, Next.js가 기본으로 붙여주지 않는다.

접근성도 화면상으로는 멀쩡했는데, 실제로 계산해보니 **입력칸 테두리 대비가
1.23 대 1**이었다(기준은 3 대 1). 시력이 약한 사람에겐 칸이 어디 있는지
안 보이는 수준이다. 색을 바꿔 3.37로 올렸다.

## 바이브코딩으로 해보니

### 빠르다

하루에 커밋 31개, 8천 줄 넘게 바뀌었다. 혼자 손으로 쳤으면 며칠 걸렸을 양이다.
특히 **문서 쓰기와 반복 작업**에서 차이가 컸다.

### 대신 내가 확인 안 하면 아무도 확인 안 한다

오늘 걸린 것들의 공통점이 있다. **화면만 봐서는 다 멀쩡해 보였다.**

| 증상 | 실제 |
| --- | --- |
| 로컬에서 인증 잘 됨 | 배포본에선 깨져 있었음 |
| 화면 멀쩡해 보임 | 테두리 대비 기준 미달 |
| 스크립트가 "완료"라고 함 | 환경변수가 하나도 안 들어가 있었음 |

마지막 건 좀 웃겼다. 환경변수 등록 스크립트가 실패해도 무조건 성공 표시를
찍고 있었다. 확인해보니 하나도 안 들어가 있었다.

그래서 중간부터는 **"다 됐다"가 아니라 "이 명령이 통과했다"**로 완료를 정의했다.

```bash
npm run build && npx vitest run && npx eslint .
```

이게 초록불이면 끝, 아니면 안 끝난 것. 확인용 스크립트도 몇 개 만들어뒀다.

### 작업은 잘게 쪼개는 게 낫다

전체를 24조각으로 나누고 하나씩 했다. 한 번에 크게 하면 어디서 틀렸는지 찾기
어렵고, AI랑 할 때는 한 세션이 길어질수록 앞부분을 놓치는 일이 생긴다.

한 조각 끝날 때마다 **인수인계 메모**를 남겨서 다음 세션이 그것만 읽고
이어받게 했다.

---

## MVP는 지금 어디까지 왔나

**되는 것**

- 가입 → 이메일 인증 → 로그인
- 아기 등록(여러 명 전환 가능)
- 수유 기록(분유·모유·이유식), 수면, 기저귀, 성장
- 타임라인과 하루 요약
- 배포된 주소에서 실제로 동작

**아직인 것**

- 내 계정으로 남의 아기 기록이 보이는지 확인 — 제일 중요한데 아직 못 했다
- 또래 비교 통계
- 커뮤니티(사진·글 공유)
- 약관과 개인정보처리방침은 초안이다

---

## 마치며

오늘의 목적은 **"한 바퀴 돌려보기"**였고, 그건 달성했다.

가늘게라도 기획부터 실제 동작까지 이어진 줄이 생겼으니, 다음부터는 이 줄에
살을 붙이면 된다. 무엇보다 **되는 걸 눈으로 봤다는 게 크다.**

바이브코딩은 확실히 빠르다. 다만 빠른 만큼 **내가 확인해야 할 것도 같이 빨리 쌓인다.**
그걸 오늘 세 번 정도 체감했다.

다음엔 계정 격리 확인부터 한다. 제일 위험한 것부터.
